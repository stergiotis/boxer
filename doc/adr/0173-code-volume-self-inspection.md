# ADR-0173: code-volume self-inspection — the artifacts, the lenses, and what each can answer

## Context

How much of what boxer ships is boxer's own code, and how much is other
people's? The tree could not answer that.

A one-off measurement session established both the numbers and that the answer
depends on which lens is used. Implementing the Go half then established two
further dependencies the first session did not see: the answer also depends on
which *artifact* is asked, because boxer is several binaries in two languages,
and on whether "code" means what somebody wrote or what a generator emitted.
Three axes, not one — so the honest output is a small family of labelled
numbers, and any single ratio is a choice of axis in disguise.

All figures below come from throwaway probes on one dev box against one build
each (go1.26.5, `linux/amd64`, the repo's `./tags`; Rust 1.96, the desktop
default plus `puffin`). They are evidence for a shape, not committed
measurements; the point of this ADR is to make them reproducible in SQL.

### The lens axis — three answers for one Go binary

- **Depended-on**, compiled source lines in the package closure: first-party
  396,247 vs third-party 1,263,112 vs stdlib 338,661 — **3.19 : 1**
  third-to-first. Of the first-party figure, 160,317 lines (40.5%) are
  generated, so against hand-written code the ratio is 5.35 : 1.
- **Shipped**, machine-code bytes in the linked `boxer` binary after
  dead-code elimination: first-party 29.5%, third-party 50.8%, stdlib
  17.5% — **1.72 : 1**.
- **Executed**, statements covered in a 58-second headless GUI session:
  **0.84 : 1** — a render loop runs *more* first-party code than
  third-party. The same instrumented binary driven through a CLI batch
  workload (`adr build`, which writes Arrow) inverts it to 2.93 : 1.

Supply-chain surface and code surface are not the same quantity: 877 modules
appear in `go mod graph`, 288 in `go.sum`, 229 in `go.mod` — but only 90
contribute a compiled line to the `boxer` binary. And a large share of
third-party "code" is not logic: `andybalholm/brotli` reports 255,835 code
lines of which 18,059 sit inside function bodies; the rest is a static
dictionary.

### The artifact axis — boxer is not one binary

Every lens above reads a Go artifact, and the Go artifacts are not the whole
program.

- **The Rust render client.** `rust/imzero2` builds a separate executable
  that the Go host launches and drives over FFFI2. It carries **19.32 MB of
  machine code** (symbol text after de-duplicating aliases, against a 19.70 MB
  `.text` section), of which the two first-party crates are **3.3%**; Rust's
  `core`/`alloc`/`std` are roughly 23% and third-party crates the rest. No Go
  lens sees any of it, and the Go answer to "how much is ours" (29.5% of
  shipped bytes) is nowhere near it.
- **Foreign artifacts embedded in a Go binary.** `h3.wasm` is 341 KB of Rust
  compiled to WASM and `//go:embed`ed into every Go binary that touches H3.
  `go_symbols` counts it as data bytes belonging to the embedding package,
  no source-line lens counts it at all, and its name section is stripped by
  the producing crate's release profile, so nothing can attribute it beyond
  a total.
- **The two Go binaries differ.** The `boxer` CLI and the imzero2 host have
  different closures; each process can only report its own.

### The authorship axis — most first-party volume was emitted, not written

- **193,627 of 730,392 committed Go lines (26.5%)** carry the conventional
  generated marker; **20,072 of 40,508 committed Rust lines (49.5%)** carry
  one too.
- The authoring surfaces behind them are small, and the amplification varies
  by two orders of magnitude: 225 lines of leeway facts-schema declaration
  produce 20,663 generated Go lines (**92×**); 2,226 lines of ANTLR grammar
  produce 67,144 (**30×**); the 6,271-line egui2 IDL produces 10,276 Go lines
  *and* 16,217 Rust lines (**4.2×**, across two languages from one surface).
- Generated volume is not uniformly logic either — 3,766 of the generated
  Rust lines are colormap lookup tables, the first-party mirror of the
  `brotli` dictionary observation above.

The generator is already recorded: the marker line carries it verbatim
(`Code generated by <tool>` — including, for ANTLR, the `.g4` it came from).
Nothing reads it today.

### What already exists

Much of the machinery is in place.
[`godepcollect`](../../public/code/analysis/golang/godep/godepcollect/collector.go)
loads the Go package closure with `go/packages` live, lazily and in-process,
and serves `keelson('go_packages')` with `import_path`, `module_path`,
`num_go_files` and a `class` column that is already
`stdlib | internal | external` — the first/third-party split at the right
grain ([ADR-0064](0064-godepview-go-dependency-explorer.md),
[ADR-0094](0094-keelson-introspection-tables.md)).
[ADR-0169](0169-continuous-coverage-keelson.md) serves the executed lens as
`coverage_pkgs` / `coverage_funcs`, keyed on `pkg_path`. **Within one
language the contrast is largely a join whose columns do not exist yet.**

What is missing is a volume measure, a shipped-code measure, a module
inventory, a reachability measure, the Rust artifact entirely, and the
authored-versus-emitted split — and these have acquisition costs and
prerequisites that differ by orders of magnitude. A deploy target has no Go
toolchain, no Cargo, no source tree and no module cache; `godepcollect` fails
there by design and reports it through `go_collection.status`.

## Design space (QOC)

### Q1 — How should the lenses be acquired?

Given prerequisites that differ by class and costs that differ by five orders
of magnitude.

**Options.**

- **O1 — One collector.** Extend `godepcollect` to compute every lens in
  its existing single cached collection.
- **O2 — Build-time harvest.** Compute everything in a dev/CI step and
  embed a generated table, the `go_package_props` /
  [`proptable`](../../public/packageprops/proptable/proptable.out.go) shape.
- **O3 — Tiered acquisition (chosen).** One provider per prerequisite
  class, each answering what its inputs allow, all joined on the natural key;
  each degrades to empty-not-absent independently.

**Criteria.**

- **C1** — Answers on a deploy target (no toolchain, no source).
- **C2** — Query-time cost, and whether one lens can regress another's.
- **C3** — Fidelity to *this* artifact rather than to a tree or a past build.
- **C4** — Maintenance surface: new packages, generators, regeneration steps.

**Assessment.** `++` strong positive, `+` positive, `−` negative, `−−` strong negative.

|    | O1 | O2 | O3 |
|----|----|----|----|
| C1 | −− | +  | ++ |
| C2 | −  | ++ | +  |
| C3 | +  | −− | ++ |
| C4 | ++ | −  | +  |

O3 wins on the two criteria that decide it. O1 couples every lens to the
toolchain, so the cheapest and most portable facts (the module list, which
costs 10 µs and needs nothing) become unavailable exactly where they matter
most; it also makes the 1.8 s line-counting pass a tax on every
`go_packages` query. O2 is cheapest at query time but describes the build
that generated it, and the committed `proptable` was found 41 packages
stale during this very session — the drift is not hypothetical. O3 costs
one more provider package per class than O1, which is the price of C1 and C3.

The tiering generalises to the Rust artifact unchanged, which is the main
reason the widened scope does not need a second framework — see §SD8/§SD9.

### Q2 — What is the unit of "code volume"?

The three axes above each admit several denominators, and the measured spread
is not a rounding difference. For the Rust client's third-party source alone:
every `Cargo.lock` crate directory is 9,255,427 lines, the crates actually
resolved for this build are 3,896,461, and the files `rustc` actually compiled
are 2,183,537 — a 4.2× spread, giving third-to-first ratios of 318 : 1,
135 : 1 and 75 : 1 for the same question.

**Options.** *(a)* pick one headline ratio; *(b)* pick one canonical
denominator per language and report only that; *(c)* report a labelled family
and refuse to sum across it.

*(a)* is rejected because every candidate headline is defensible and they
disagree by 4×, so the number would be an argument rather than a measurement.
*(b)* is rejected because the denominators answer genuinely different
questions — "what did we take on" (locked), "what does this build depend on"
(resolved), "what got compiled" (depfiles) — and picking one discards the
others at acquisition time, when they cost almost nothing to keep. **(c) is
chosen**: every row carries the artifact, the lens and the denominator it was
measured under, and nothing in the schema invites a cross-artifact total.

## Decision

**The frame.** One table per (artifact, lens), keyed on that artifact's
natural unit — import path for Go, crate for Rust — and carrying an explicit
denominator label. All tables share one `party` vocabulary
(`first | third | runtime`, where `runtime` is Go's stdlib or Rust's
`core`/`alloc`/`std`) so the same question can be asked of each. Nothing sums
across artifacts, and no view offers a single repository-wide ratio.

Subsidiary decisions follow, one per prerequisite class.

### SD1 — `go_modules`: the module inventory of the running binary ✓

`runtime/debug.ReadBuildInfo()` — **10 µs, needs nothing** — yields the main
module, every dependency module with version and checksum, any `replace`,
and the build settings. Measured against the `boxer` binary it reports
exactly the **90** modules that contribute compiled packages, agreeing with
the toolchain-derived closure. Columns: `path`, `version`, `sum`,
`replaced_by`, `is_main`. `FreshnessStatic` — immutable for the process.

This is the only lens that is both free and always available, so it is the
floor: on a stripped-down deploy target with no source, `go_modules` still
answers "what third-party code is in this process". Rust has no equivalent
(§SD9), which is the sharpest asymmetry between the two artifacts.

### SD2 — `go_symbols`: what the linker actually kept ✓

`debug/elf` over `os.Executable()` reads the binary's own symbol table —
**31 ms and 38 MB RSS on the 126 MB `boxer` binary**, 122,408 sized
symbols. Text bytes attributed this way agree with `go tool nm` to within
0.01%. No toolchain, no source, no module cache.

Package grain: `pkg_path`, `module_path`, `num_symbols`, `text_bytes`,
`data_bytes`. Text and data are separate columns because conflating them
lets one zero-filled buffer dominate every real package —
`crypto/internal/fips140/drbg.memory` is a 32 MiB data symbol, 42% of the
binary's sized bytes and not code at all.

Module attribution is exact against §SD1's in-binary module list; package
attribution is heuristic (the segment before the first `.` after the last
`/`) and over-splits generic instantiations and linker-synthesised symbols.
A `module_attribution` column reports which was used, so the difference is
visible in SQL rather than silent. `FreshnessStatic`.

### SD3 — `go_packages` volume columns: how much source backs it ✓

Added to the existing table: `code_lines`, `comment_lines`, `blank_lines`,
`generated`, `other_lang_lines`. Lines are classified with `go/scanner`
rather than by regex, so `//` inside a string literal is never counted as a
comment; `generated` is the conventional `Code generated … DO NOT EDIT.`
marker, which matters because it separates 160k generated first-party lines
from the ~236k hand-written ones. `other_lang_lines` counts the C/C++/asm
files compiled with a cgo package — 376,887 lines in the repo-wide closure,
invisible to any Go-only count.

**The pass gets its own lazily-populated cache, not `godepcollect`'s.**
Bare `go list` over the closure costs 0.39 s; adding full scanner
classification over ~7,000 files costs **1.8 s more**. Folding that into
the existing collection would take it from ~1.4 s to ~3.2 s against a 5 s
first-wait budget, making every `go_packages` query pay for a column most
queries do not read. Separate caches keep one lens from regressing another,
which is the C2 half of Q1.

### SD4 — `go_reach`: reachability, out of process

RTA over whole-program SSA from `main` and `init`, package grain:
`funcs_total`, `funcs_reached`, `lines_total`, `lines_reached`. It answers
what §SD2 cannot — *which* code could run, at source-line grain rather than
byte grain — and it is the lens vulnerability tooling uses, so it is worth
having despite its cost.

Measured: **7.07 s wall, 49.5 s CPU, 4.15 GB peak RSS.** The wall time is
tolerable; the resident set is not, inside a long-lived GUI process whose
frame budget is 16 ms and whose memory Go's scavenger returns lazily. Worse,
`golang.org/x/tools/go/ssa` is **absent from the imzero2 host closure**
today, so an in-process implementation would add the analysis machinery to
the very binary it measures.

So the computation runs **out of process**, driven by a
[`bgjob.Runner`](../../public/keelson/runtime/bgjob/bgjob.go) over the
[ADR-0038](0038-keelson-background-task-primitive.md) task protocol: the
job is observable, cancellable and progress-reporting, the 4 GB is isolated
in a child that the OS reclaims on exit, and the host binary gains no new
analysis dependency. The child is a `boxer code analysis golang reach`
subcommand emitting JSON on stdout, resolved through the
[external-binary chokepoint](../../public/extbin) rather than assumed to be
`os.Executable()` — the GUI host is a different binary from the CLI and
need not carry the subcommand.

Until a run completes the table is empty and a `status` column reports
`idle | running | ready | failed`, mirroring `go_collection`'s sticky-failure
discipline: a missing or wedged child costs one attempt, not one per query.

There is no Rust counterpart and none is planned — see §SD8.

### SD5 — Build identity, so disagreement is legible ✓

§SD1 and §SD2 describe the **binary**; §SD3 and §SD4 describe the **source
tree the process happens to sit beside**. On a dev box these diverge the
moment the tree is edited after building, and on a deploy target the tree is
absent entirely. `keelson('build')` already carries `vcs_revision` and
`vcs_modified`, and `go_collection` carries its own collection metadata; a
join that mixes the two lenses can compare them and say so. Nothing silently
reconciles them.

§SD8 makes this sharper rather than merely adding to it: the Rust client is a
*different artifact*, built at a different time by a different toolchain, so
"is this the client that is actually running" is a question the Go tables
cannot answer from their own contents.

### SD6 — Viewing

An applet book ([ADR-0132](0132-sqlapplet-sql-defined-applets.md)) over the
tables plus `coverage_pkgs`: a party-split overview, a module and crate
inventory ranked by shipped bytes, a treemap
([ADR-0166](0166-play-treemap-panel.md)) sized by source lines and coloured
by party, and the lens contrast as one row per module. The contrast is a SQL
join, not new render code — which is the point of keying every lens on the
natural unit.

Widened scope adds two views and one prohibition: an artifact selector
(Go binary / Rust client), an authored-versus-emitted view over §SD10, and no
view that adds a Go number to a Rust one.

### SD7 — Persistence deferred

The tables are process-scoped snapshots. "Is the third-party share growing?"
is a history question and needs the [ADR-0169](0169-continuous-coverage-keelson.md)
§SD6 facts tee, still unbuilt. Recorded as the natural next step, not built
here; nothing in the milestones depends on it.

### SD8 — `rust_symbols`: the peer binary the Go lenses cannot see

The §SD2 tier ports to the Rust client almost unchanged, and it is the only
Rust lens that describes a shipped artifact rather than a tree. The ELF
reading is language-agnostic — `codevol`'s existing file-path core is reused
as-is — and three things differ.

**Attribution is by crate, and the mangling must be decoded.** Rust's legacy
scheme (`_ZN…17h<hash>E`) carries the *defining* crate in the symbol name, so
attribution needs no second table and no toolchain. Taking the first path
component naively reaches 70% of text bytes; decoding the `$LT$`/`$u20$`
escapes and cutting `<Self as Trait>::method` at the ` as ` reaches **94.4%
of symbols and 96.2% of text bytes** in about 60 lines. The residue is v0
mangling (2.5% of text) and impls on bare type parameters (1.6%). This is
*better* than §SD2's package attribution, not worse, and it is exact at the
crate grain — but it commits to a convention worth stating: an impl
attributes to the crate the impl is written in, and a monomorphised generic
attributes to the crate that defines it, not to the crate that instantiated
it.

**Addresses must be de-duplicated.** 4,700 symbols share an address with
another symbol (identical-code folding and aliases), worth 1.33 MB. Summing
naively gives 20.65 MB against a 19.70 MB `.text` section — 5% high, and the
top-crate ranking shifts. De-duplicating by address gives 19.32 MB, within 2%
of the section, the remainder being padding and PLT stubs. The Go linker does
not alias at this rate, so §SD2 needed no such step.

**The path comes from configuration, not from `os.Executable()`.** The client
is a peer process at
[`application.Config.ClientBinary`](../../public/thestack/imzero2/application/config.go),
so the provider reads a path
it is told about and gains two failure modes §SD2 has no analogue for: no
client configured (CLI-only compositions), and a configured client that is not
the one running. Both degrade to an empty table with a `status` reason.

Columns: `crate`, `party`, `num_symbols`, `text_bytes`, `data_bytes`,
`attribution`, plus `artifact` naming the file read. No reachability
counterpart is planned: `cargo-bloat` reads the same symbol table this does
while adding a toolchain prerequisite, and the release profile emits no DWARF,
so there is nothing richer to read without a build change.

A build-hygiene item surfaced by this measurement, recorded here because it
was found here and belongs to whoever owns the build rather than to this ADR:
panic-location strings embed the build user's absolute home directory into the
shipped client. `trim-paths` / `--remap-path-prefix` is the fix.

### SD9 — `rust_crates` and Rust source volume

**There is no §SD1 floor on the Rust side.** Rust has no
`ReadBuildInfo()`, so the cheapest lens cannot describe the binary. Three
substitutes, in ascending cost:

- **`Cargo.lock`** — a plain TOML parse, no toolchain. Describes the *tree*,
  and overstates: 676 locked packages against the 421 crates actually resolved
  for this build. Honest only if labelled as a tree lens, which is what the
  denominator column is for.
- **Panic-location strings in the binary** — recovers 178 of 421
  crate-versions with no build change and no source, but only for crates
  carrying a panic site. Partial by construction; not worth a table on its own,
  and already implied by §SD8's crate list.
- **A build change** — `cargo auditable` (a `.dep-v0` section) or a `build.rs`
  const. This is the only thing that would give Rust a real §SD1 floor. It is
  one line of build script for a property the Go side gets free, and it is
  **deferred, not rejected**: §SD8 already names every crate that contributed
  code, so the marginal gain is versions, not membership.

Chosen for now: `rust_crates` from `Cargo.lock`, labelled `denominator =
'locked'`, joined to §SD8 on crate name (normalising `-` to `_`; a crate whose
`[lib] name` differs arbitrarily from its package name will not match, and is
reported rather than guessed).

**Source volume needs Cargo and the registry cache**, the §SD3 tier.
`cargo tree --offline -e normal --target …` resolves the build's actual
dependency set in **0.30 s** — the Rust `go list`. Per-file volume then has
two denominators worth keeping, both already on disk: whole crate directories
for the resolved set (3,896,461 lines over 12,689 files) and the files
`rustc`'s own depfiles name (2,183,537 lines over 7,033 files, 56% of the
former). Against 28,955 first-party lines that is 135 : 1 and 75 : 1
respectively. A Rust line classifier has to be written — nested block
comments, `r#"…"#` raw strings, and `'a` lifetimes against `'a'` char
literals — and until it exists the numbers above are the crude
non-blank-non-`//` count and must be labelled as such.

### SD10 — `generator`: the authored surface behind the emitted volume

One column, on `go_packages` beside the existing `generated` flag, parsed from
the marker line the §SD3 pass already reads: `Code generated by <tool>` yields
the tool, and ANTLR's variant additionally yields the input grammar. Free at
acquisition, and lenient by necessity — the tool field is free-form prose that
nothing validates, so the values in the tree range from an import path to
`copy paste` (and, in four files, `copy pase`). The column groups a string
somebody typed; where the marker does not match at all, it reports `unknown`
rather than failing the pass.

That turns "how much of the first-party total did anyone write" from a bespoke
run into a `GROUP BY`, and it is the axis with the widest spread: 92× for the
leeway facts schema, 30× for the ANTLR grammars, 4.2× for the egui2 IDL. The
egui2 case is the one that justifies putting this on the same footing as the
other lenses — a single 6,271-line authoring surface emits into *both*
artifacts, so a Go-only or a Rust-only reading attributes it twice or not at
all.

Deliberately **not** attempted: a table relating each generated file to its
input files. The marker names the tool, not in general the inputs, and
recovering the relation would mean modelling every generator. The tool name is
enough to group by, and the input surface is a `git ls-files` away when a
specific ratio is wanted.

### SD11 — Embedded foreign artifacts

`h3.wasm` is 341 KB of Rust inside every Go binary that touches H3, and it is
stripped of its name section, so per-crate attribution is impossible without
rebuilding the producing crate without `strip`. No table: the honest record is
a row in §SD2's data bytes (which already counts it, under the embedding
package) plus this paragraph saying what that row contains. Recorded so that a
future reader who notices a 341 KB data symbol has an explanation rather than
a mystery.

### Milestones

- **M0 — `go_modules` (§SD1).** ✓ Smallest, no prerequisites, immediately useful.
- **M1 — `go_symbols` (§SD2).** ✓ Heuristic attribution first, reconciliation second.
- **M2 — `go_packages` volume columns + separate cache (§SD3).** ✓
- **M3 — the `generator` column (§SD10).** One regex on a pass that already runs.
- **M4 — `rust_symbols` (§SD8).** Demangler, address de-duplication, configured path.
- **M5 — `rust_crates` + Rust source volume (§SD9),** including the line classifier.
- **M6 — the applet book widened (§SD6):** artifact selector, authored-vs-emitted view.
- **M7 — `go_reach` subcommand, bgjob wiring, table (§SD4).** Last: highest cost, narrowest use.

M3 moved ahead of the Rust work because it is nearly free and touches the
largest single distortion in the numbers already being served. The first cut
of the book landed with M0–M2 (four applets in `bookcodevol`, plus `go-volume`
in the godep book); M6 widens it rather than starting it.

## Alternatives

- **A single cross-language ratio.** The units do not commensurate (Go
  compiled lines against Rust compiled lines against WASM bytes), the
  artifacts are different processes built at different times, and the four
  candidate denominators disagree by 4×. A sum would be a number nobody could
  act on. This is Q2 option *(a)*, and the schema is shaped to make it
  awkward rather than merely discouraged.
- **`Cargo.lock` as the Rust closure.** Rejected on measurement, not
  principle: 676 locked against 421 resolved, and 4.2× on source lines. Kept
  as an explicitly labelled tree lens (§SD9), not as *the* answer.
- **`cargo-bloat` for the Rust shipped lens.** It reads the same symbol table
  §SD8 reads, and adds a Cargo prerequisite to the one Rust lens that
  currently has none.
- **DWARF for Rust crate attribution.** Complete in principle; the release
  profile emits no debug sections, so there is nothing to read without a build
  change, and symbol-name demangling already reaches 96% of bytes.
- **RTA in-process in the GUI host.** 4.15 GB resident inside a 16 ms frame
  budget, and it would add `go/ssa` to the host binary it measures.
- **Reach via a build-time harvest into a generated table.** Cheap at query
  time, but describes a past build; the sibling `proptable` was 41 packages
  stale in this session, which is the failure mode in evidence.
- **Per-symbol rather than per-package `go_symbols` / `rust_symbols`.** 122k
  and 49k rows respectively are affordable, but every question asked so far is
  an aggregate; deferred rather than rejected.
- **Reusing the ADR-0169 coverage meta blob as the function inventory.** It
  enumerates every instrumented function with a line span and would give
  §SD4's grain almost free — but only in a `-cover` build, so it cannot be
  the general answer. Worth revisiting as a fast path when instrumented.
- **A `code_volume_*` table family parallel to `go_packages`.** A second
  grain to keep in sync, and every question becomes a join, for no gain
  over columns on the table that already carries `class` and `module_path`.
- **A generated-file-to-input-file relation.** Would require modelling every
  generator; the tool name (§SD10) supports the grouping, and specific ratios
  are a `git ls-files` away.

## Consequences

### Positive

- The lens contrast becomes a SQL join over existing keys within an artifact,
  with no new render surface, and joins onward to `coverage_*` and
  `go_imports`.
- The two cheapest Go lenses need no toolchain and no source, so a deployed
  process can answer "what is in me" — which `godepcollect` alone cannot. The
  Rust shipped lens has the same property.
- Dead third-party weight becomes queryable. The measurement that motivated
  this ADR found `sirkon/dst` linked into every binary at 0% reachability;
  that class of finding becomes a `WHERE` clause instead of a bespoke run.
- The authored-versus-emitted split (§SD10) costs one column and corrects the
  largest distortion in the first-party figure — 26.5% of committed Go and
  49.5% of committed Rust.

### Negative

- Six acquisition paths with six failure modes, each needing its own status
  surface and its own empty-not-absent test.
- `go_symbols` and `rust_symbols` couple to ELF layout and to symbol naming; a
  stripped binary yields an empty table. Nothing in the tree strips the two
  hosts today, but `h3bridge` does strip (§SD11), so the failure mode is
  already present in the repository rather than hypothetical.
- §SD8 reads a path from configuration, so it can silently describe a stale
  client. The `artifact` column reports what was read; comparing it to what is
  running is left to the reader.
- §SD4 adds a subprocess dependency to a GUI host, with the extbin resolution
  and failure handling that implies.
- A Rust line classifier is a hand-written lexer with no `go/scanner` to lean
  on, and its edge cases (nested block comments, raw strings, lifetimes) are
  exactly the ones a naive implementation gets wrong quietly.

### Neutral

- Numbers are per-artifact, never per-repository. The `boxer` CLI, the imzero2
  host and the Rust client each report their own, and the schema does not
  offer a total.
- `rust/h3bridge` and `rust/watermark` (~3k lines combined) are covered by
  §SD9's tree lens but produce no long-lived process to read, so they have no
  shipped lens.

## Migration — Tier 1

- **Breaks.** Nothing. Five tables are new; the `go_packages` changes are
  additive columns.
- **Path.** Nothing to migrate. An applet selecting `*` from `go_packages`
  sees the added columns.
- **Regeneration.** `doc/env-vars.md` for the §SD4 knob. No FFI, no codegen,
  no Rust rebuild.
- **Old shape.** Not applicable.

## Verification plan — Tier 1

- **Lane.** Default `go test` for the providers (row-level tests over
  fixtures, plus the empty-not-absent gate each table needs); the
  `//go:build integration` lane for the lenses that read real artifacts —
  `go_symbols` against a built binary's own ELF, `rust_symbols` against the
  built client, `go_reach` against a small probe module — since all need a
  real build to exist.
- **What would fail.** `go_modules` row count diverging from `go version -m`;
  `go_symbols` text-byte totals diverging from `go tool nm` beyond a tolerance
  (they agreed to 0.01% when measured); `rust_symbols` text bytes diverging
  from the `.text` section size beyond ~2% *after* address de-duplication
  (19.32 MB against 19.70 MB when measured — before de-duplication the same
  check fails at 5%, which is the regression this gate exists to catch);
  `rust_crates` row count diverging from `cargo tree` for the same feature
  set; a `go_packages` query exceeding its first-wait budget once the volume
  cache is separate.
- **Gap.** Attribution quality is reported, not gated — `module_attribution`
  for §SD2, `attribution` for §SD8 — because the only way to check either is
  the reconciliation the column says is absent. For §SD8 the measured coverage
  (96.2% of text bytes) is a baseline to notice regressions against, not a
  threshold to enforce, since it moves with every toolchain bump.

## Updates

### 2026-08-06 — M0–M2 and the book landed; four refinements

`codevol` (the pure analysis: `Modules`, `ReadSelfSymbols`, `CountFiles`),
the `go_modules` / `go_symbols` providers, the `go_packages` volume columns
behind their own lazy cache, and two applet suites —
`bookcodevol` (4 applets) plus `go-volume` in the existing godep book.
The live godep gate runs the source-volume buffer against this repository
and reproduces the Context's numbers: third-party 1,263,112 code lines
(exact match), first-party 397,982, ratio 3.17, 40.3% of first-party
generated. Implementation changed four things:

- **`go test` links the binary it runs without a symbol table.** Confirmed
  by inspection: `go test -c` produces a `.symtab`, the binary `go test`
  actually executes does not, so `ReadSelfSymbols` always fails under the
  default lane. §SD2's tables are therefore untestable by self-reading, and
  the providers take an injectable `CodevolSourceI` (the `CoverageSourceI`
  pattern) so the gate can serve a fixture. Real-symbol assertions live in
  the integration lane, which builds a binary and reads it. §SD8 inherits
  this: its source is a configured path, so a fixture serves it naturally.
- **Module attribution is exact; package attribution is not.** §SD2
  originally proposed reconciling symbol names against `go_packages`.
  Unnecessary: a longest-prefix match against the module list the binary
  *already* declares (§SD1) resolves the owning module exactly, with no second
  table and no toolchain — and the module is the grain the first-vs-third
  question is actually asked on. `pkg_path` stays heuristic and is labelled as
  such; the `attribution` column became `module_attribution`.
- **Laziness came for free from the projection.** `introspect.Table.Build`
  only invokes getters for projected columns, so the volume columns' cost
  falls only on a query that selects one — a cleaner guarantee than the
  budget §SD3 assumed it would need. The pass runs its own `packages.Load`
  rather than extending the graph collection, which also keeps machine-local
  absolute paths out of the facts-bound manifest DTO.
- **`keelson('build')` already carried the identity columns** §SD5 wanted
  (`vcs_revision`, `vcs_modified`), so `go_modules` does not duplicate them.

Two tables landed in the *static* provider set rather than beside
`providersgodep`, which the ADR did not anticipate: `go_modules` and
`go_symbols` have no heavy dependencies, so unlike `go_packages` they can
ship in an appliance build. That is the tiering paying off in the place it
was least expected — the cheap lenses answer where the expensive one is not
even registered.

### 2026-08-06 — scope widened from Go to the whole tree

The ADR was written as a Go-only decision, with the Rust client noted as out
of scope. Measuring the Rust side to size that follow-up showed the omission
was not a gap at the edge but a second and third axis through the middle: the
program is several artifacts in two languages (§SD8, §SD11), and a quarter of
the Go and half of the Rust first-party volume is emitted rather than written
(§SD10). Q2 and §SD8–§SD11 are new; §SD1–§SD7 are unchanged in substance, and
the milestone order changed to put the near-free `generator` column ahead of
both the Rust work and `go_reach`.

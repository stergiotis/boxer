leeway is a columnar mapping for semi-structured data. Measured against a database's own JSON type over 100 million Bluesky Jetstream events — 1.2 billion attributes — on one laptop. Source: the trial, logbook.

Why this shape suits logs and wide events

1. You search for values whose path you do not know

“Find this trace id / request id / user, anywhere in the corpus” is the bread-and-butter log query, and it is where the two representations diverge most. At 100M documents, on a full scan with no index on either side:

find a value at any path1.42 s1116.61 s786×

The last three rows matter most. Two of these questions cannot be asked of the JSON type at any speed, and the third takes 18.8 minutes against 0.11 seconds. Schema-on-read inference is worse again — it can answer 6 of 14 queries, because it types the stable backbone of a document and gives up on the part that actually varies.

2. You filter on several fields and retrieve

The other log shape, and the first stage of any tiered query: filter on several attributes, return the matching events. 100M documents, three ways of storing them, at three predicate densities:

criteriaevents outone row per attributeJSON typeone row per document
4, incl. a rare user70.29 s0.63 s2.07 s
4, incl. the top poster10,9360.40 s0.69 s2.18 s
3, no user filter8,377,9291.95 s0.97 s2.45 s

Read that as a comparison of unindexed layouts only. The attribute-per-row table is sorted (path, doc); the other two are not. A JSON column can be sorted on the paths a query filters, and given that index it prunes to 5 granules of 1225 and answers the same four-criteria lookup in 0.03 s — 3.3× ahead of the attribute-per-row layout, not behind it.

So the real split is whether the filter paths are known when the table is created. Known: sort the JSON or typed columns on them and nothing here beats it — but that index serves only the paths it was built for. Not known: (path, doc) is the workload-agnostic alternative and beats every unindexed option, because it is the only one of the three whose index helps a filter on any path. The document-per-row layout is last in every configuration and cannot be given this index at all — the path lives inside an array.

Which is the same axis as the rest of this page: an index helps when the path is in the query; the exploded layout is what you reach for when it is in the data. Both layouts can be kept at once — converting 100M documents takes 50.8 s at a bounded 5.4 GB, and the copy is smaller than the original (0.70×), so carrying both costs 1.70× one.

3. The advantage widens with scale

Going from 10M to 100M documents — ten times the data — the two representations scale differently, and it is the JSON type that degrades:

queryleeway 10M → 100MJSON type 10M → 100M
count every leaf0.06 → 0.10 s (1.7×)3.04 → 39.89 s (13.1×)
find a value at any path0.16 → 1.42 s (8.9×)111.1 → 1116.6 s (10.0×)
census of every path0.36 → 3.17 s (8.8×)2.83 → 39.79 s (14.1×)

leeway scales at or below linear on every one; the JSON type scales at or above it. So the ratios reported here are a floor, not a ceiling: at 10M find-a-value was 695×, at 100M it is 786×.

4. Events are heterogeneous and the schema drifts

leeway holds a mixture of document shapes uniformly — that is what it is for. The comparison shapes do not: the fastest published JSON configuration declares five typed paths and max_dynamic_paths = 0, buying its speed by giving flexibility back, and schema-on-read inference declined to type the varying subtree at all.

Storage: no penalty

At 100M documents, excluding a row-identity column the JSON arm has no counterpart for, leeway holds the corpus in 10.95 GiB against the JSON type's 10.31 GiB — 1.06×, the same ratio seen at 10M. Only 2.1 % of a leeway table is its addressing machinery; the rest is payload either representation must store. Against DuckDB's text-backed JSON type, leeway is half the size.

Semantics: a strict superset of JSON

JSON has six types. leeway's canonical type system covers temporal, network and decimal types with declared widths, and its mapping distinguishes null from undefined — a distinction JSON itself does not carry.

Memberships: gradual typing for the address

In JSON an attribute has exactly one address: its path, a string. In leeway the address is a membership, and there are 8 membership specs spanning a range of strictness. You can start at the loose end and tighten later without touching the values.

specwhat the address iswhat it costs you
…VerbatimHighCardParameters (used here)the path as a literal string, plus a free-form parameter channelnothing — no vocabulary to declare
LowCardVerbatima literal from a small setdictionary encoding, nothing else
LowCardRef / HighCardRefan id into a controlled vocabularyyou must define the vocabulary
…RefParametrizeda vocabulary id plus typed parametersvocabulary + parameter schema

And a section may carry several memberships at once, so an attribute can be addressed by path and by unit and by tenant and by role simultaneously — each independently queryable, co-indexed in the same row, no join. Primary and secondary membership sets are themselves declarable. This whole trial ran on one membership per attribute, the loosest spec in the table — the entry-level configuration — and still produced the numbers above.

Tagging: what a value is, and what it is for

Beyond types, leeway carries two declarative tag vocabularies that a JSON column has no place to put:

vocabularytagsexamples
value aspects — what a value is, per column61 scale of measurement (nominal / ordinal / interval / ratio); Unicode normalisation form and case-folding; natural vs surrogate vs content-addressable key; ML feature encodings and scalings; expected lifespan; anonymised; mandatory vs optional
use aspects — what a section is for56 privacy, compliance, policy, security, risk, audit; lineage and provenance (activity / agent / entity / relation); slowly-changing-dimension strategy; source-of-truth class; log, metrics, observability; ownership and org role
encoding aspects — how it should be stored23 delta / double-delta, dictionary, low-cardinality within or across records, light vs heavy general compression

These are schema-level declarations, not conventions in a field name: the DDL generator consumes the encoding aspects, and the others travel with the data as machine-readable intent. Governance questions a JSON column answers with a naming convention and a wiki page — which columns are personal data, which are the source of truth, which are ordinal and must not be averaged — are declared here.

Three honest limits: the standard mapping cannot tell an empty object or array from an absent one (a Lossless variant adds those); none of the tagging above was exercised by these measurements; and the multi-membership capability was not either — raising it makes single-address lookups dearer, so it is a trade to measure rather than a win to assume.

Portability

The same mapping and the same fourteen queries ran on ClickHouse, DuckDB and DataFusion. All fourteen reproduce the reference answers on every engine, with two explained differences, across a 2.7× latency band. DataFusion has no JSON type at all and not one higher-order array function among its 433 routines — leeway's data still reads there.

Where it loses, and what recovers it

When a query names its paths — the classic dashboard aggregate — a typed column beats leeway by 3.0×. It is the typing that wins, not the index: removing the clustered index from the published entry costs only 1.24×.

The gap is recoverable rather than structural. Materialising the queried paths as columns is worth 3.8–13.8×, re-keying on them a further 1.07–1.76×, and together they put the leeway table at 0.59–1.18× of the published tuned entry at 0.954× its storage — parity, faster on two of the five benchmark queries.

How big are the design decisions, generally?

Across 96 pairwise comparisons computed from the trial's own timings, 62 % land inside 0.5–2.5×. They are not evenly spread, and the ordering is the useful part:

decisionworst casecharacter
which engine3×the cheapest decision measured
how the query is written5×tuning; fixable by a rewrite
storage format (Parquet vs native)1.36×and Parquet is 2.2× smaller
row layout44×mostly modest, with a tail
representation920×almost all cliff — 8 of 14 beyond 10×

Spend the design attention on representation and on what the target can express; treat engine choice as cheap. That is close to the inverse of how such choices are usually sequenced.

What this did not measure

The read profile above fits log analytics unusually well. The write and lifecycle half is untested, and it is the half log analytics leans on hardest:

  • Ingest throughput — 75–83k documents/s, single process, already flagged as the first thing to parallelise. This workload is read-only; log analytics is ingest-dominated.
  • No retention, partitioning, compaction, streaming append or mutation of any kind.
  • No concurrency — every figure is one query at a time — and no cold-cache runs.
  • One category per attribute — the multi-category capability log events would lean on (service, level, region, tenant as orthogonal axes) was never exercised, and raising it makes single-axis lookups dearer, so it is a trade to measure rather than a win to assume.

So: true on the read side, unproven on the write side.

leeway as a JSON and log-analytics representation

One page of measured results from the leeway-on-a-second-substrate trial. 10 million Bluesky Jetstream documents, 121.2 million attributes, three engines. Every latency is a hot run; there is no cold column, because the measuring box grants no passwordless cache drop. Detail and evidence: logbook.

The short version

leeway stores semi-structured data as flat typed lanes rather than as documents. Against a database's own JSON type it is about the same size on disk, several hundred times faster when the query does not know the path in advance, and about three times slower when it does — a gap that a materialised projection closes. It answers questions two of the three JSON types cannot express at all.

Why this matters for log analytics

Log and wide-event workloads have three properties that decide the comparison, and the measurements land on all three.

1. You search for values whose path you do not know

“Find this trace id / request id / user anywhere in the corpus” is the bread-and-butter log query. It is also the trial's single largest ratio.

The last two rows are the important ones: ClickHouse's JSON type cannot express those questions at all, at any speed. Schema-on-read inference is worse — it answers 6 of 14 queries, because it types the stable backbone of a document and gives up on the part that actually varies.

2. You retrieve candidate rows, then narrow

A tiered query — filter on several fields, return the matching events — is the other log shape. Stored one row per attribute, leeway turns each filter into a sorted-index seek:

The tighter the filter, the bigger the win. Both layouts can be kept at once: converting 100M documents to the exploded form takes 50.8 seconds at a bounded 5.4 GB of memory, and the copy is smaller than the original (0.70×), so carrying both costs 1.70× one.

3. Events are heterogeneous and the schema drifts

leeway holds a mixture of document shapes uniformly — that is what it is for. The comparison shapes do not: ClickHouse's fastest JSON configuration declares five typed paths and max_dynamic_paths = 0, buying its speed by giving flexibility back, and DuckDB's inference declined to type the varying subtree at all.

Semantics: a strict superset of JSON

JSON has six types. leeway's canonical type system covers temporal, network and decimal types with declared widths, and its mapping distinguishes null from undefined — a distinction JSON itself does not carry. An attribute can also belong to several orthogonal categories at once, where a JSON document gives it exactly one path.

Two honest limits: the standard JSON mapping cannot tell an empty object or array from an absent one (a Lossless variant exists and adds those), and the multi-category capability was not exercised by this trial — every arm ran with exactly one category per attribute.

Portability

The same mapping and the same fourteen queries were run on ClickHouse, DuckDB and DataFusion. All fourteen reproduce the reference answers on every engine, with two explained differences. Latency spans a 2.7× band across the three.

DataFusion has no JSON type at all and not one higher-order array function among its 433 routines — leeway's data still reads there, in a rendering that uses no array functions whatsoever.

Where it loses, and what recovers it

When a query names its paths — the classic dashboard aggregate — a typed column beats leeway by 3.0× (0.42 s against 1.24 s; it is the typing that wins, not the index, which is worth only 1.24×).

That gap is recoverable rather than structural. The sibling trial measured the fix: materialising the queried paths as columns is worth 3.8–13.8×, re-keying on them a further 1.07–1.76×, and together they put the leeway table at 0.59–1.18× of JSONBench's own tuned ClickHouse entry at 0.954× its storage — parity, faster on two of the five queries.

How big are the decisions, generally?

Across 96 pairwise comparisons computed from the trial's own timings, 62 % land inside 0.5–2.5×. But they are not evenly spread, and the ordering is the useful part:

Spend the design attention on representation and on what the target can express; treat engine choice as cheap. That is close to the inverse of how such choices are usually sequenced.

What this trial did not measure

The read profile above fits log analytics unusually well. The write and lifecycle half is untested, and it is the half log analytics leans on hardest:

  • Ingest throughput — 75–83k documents/s, single process, and already flagged as the first thing to parallelise. The workload here is read-only; log analytics is ingest-dominated.
  • No retention, partitioning, compaction, streaming append or mutation of any kind.
  • No concurrency — every figure is one query at a time — and no cold-cache runs.
  • Membership arity 1 — the multi-category capability that log events would lean on (service, level, region, tenant as orthogonal axes) was never exercised, and raising it makes single-axis lookups dearer, so it is a trade to measure rather than a win to assume.

So: true on the read side, unproven on the write side. Closing it needs a sustained-ingest arm with retention and a time-ordered key, at arity greater than one — a different trial, on a corpus JSONBench cannot supply.

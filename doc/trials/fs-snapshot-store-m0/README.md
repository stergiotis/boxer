# fs snapshot store — M0 verification trial

[ADR-0198](../../adr/0198-fs-snapshot-store.md) records the decision to write a
walk of an `fs.FS` into facts-shaped ClickHouse tables. Its M0 milestone
([plan page](../../adr-background-work/iofs-clickhouse-snapshot-store-plan.md))
asks eleven questions the design assumed the answers to, and defers five
sub-decisions (SD11) until they are answered. This directory is the protocol
for asking them, and `runs/` holds what the answers were.

The trial's product is decisions, not a benchmark score: most checks are
pass/fail against a live server, three are measurements whose only job is to
tell an order of magnitude, and the toolbelt half — which of the repository's
own generators and read surfaces carry the shape, and where they refuse —
turned out to lead.

## 1 Question and scope

1. **The trial proper.** Do the repository's own generators carry a
   facts-shaped store the facts writer does not own — `recordstore/gen` with
   the `boxer.facts` `TableDesc` under a different table name, its own engine
   clauses and its own `EnsureTable`? Where it refuses, what does it need?
2. **The side-product.** What do a facts-shaped block table and a bespoke one
   actually cost against each other, and does ClickHouse behave the way the
   design assumed on `TTL`, materialised columns, materialised views and
   outer joins?

In scope: the eleven checks of the plan page §M0, plus the per-mount purge
(the design promises it and SD10 proposes a projection that turns out to
block it). Out of scope: anything that writes production code — M0 exists to
be run *before* the vocabulary and the stores are authored.

## 2 The workload

Four shapes, all against one live ClickHouse:

- **Blocks.** 200 rows of incompressible bytes at 1 MiB and at 256 KiB, with
  `index_granularity = 1`, in the facts `blobArray` value stream and in a
  plain `String` column, for the compressed-block and point-read questions.
- **Entries.** Up to 200 000 paths under one mount and 2 000 mounts of 25
  entries each, for the key, the materialised tree columns, the skip index,
  the materialised view and the many-rows-per-`(id, ts)` question.
- **One representative mount.** This repository's own `public/` tree — 3 712
  files, 31.1 MiB of mixed Go, generated SQL, prose and a few binaries —
  walked, cut into blocks and hashed, for the compression question. The
  corpus is committed code, so a later run reproduces it exactly by checking
  out the same commit; it is named by `M0_CORPUS_ROOT`, so a different one
  can be substituted (and must then be recorded in the logbook).
- **A three-file tree over a pipe**, for the rclone contracts.

## 3 System under test and arms

| Arm | What it is | Answers |
| --- | --- | --- |
| `fsmeta` / `fsdata` facts-shaped | the `boxer.facts` `TableDesc` on a table the store owns, generated by `recordstore/gen` with `SharedRA`, `Input.DDL` and `ExternallyProvisioned = false` | checks 1, 4, 5, 6, 8, 9 |
| `fsdata_bespoke` | seven plain columns, same key, same partitioning, same `TTL`, same transport | the comparison arm for checks 1, 8, 9 |
| plain MergeTree scratch tables | no leeway at all | checks 2, 3, 7 |
| `rclone serve sftp --stdio` | stands in for the M5 head — a working SFTP-over-stdio server, so rclone's `sftp` *backend* meets the same wire contract our head will | check 11 |

Standing hypotheses, all of which a run may refute: one block is one
compressed block; `ttl_only_drop_parts = 1` is safe because every partition
expires as a whole; materialised columns are invisible to the store; the
generator accepts the facts `TableDesc` under a foreign table name; the
facts shape costs a small constant factor on insert, not an order of
magnitude.

## 4 Method

- **Environment.** Engine and tool versions, host CPU and memory, and the
  server settings the checks read are captured per run in
  `runs/<date>/environment.md` — never hostnames or personal paths. Host
  load at measurement time belongs there too: §check 8 is sensitive to it.
- **Per run.** Every check writes its output verbatim to
  `runs/<date>/check-NN-*.txt`; the logbook entry states pass/fail and the
  finding, and points at the file.
- **Idiom rule.** The facts arms must go through the generated store —
  `EnsureTable`, `Begin`/`Add`/`Commit`, `Flush`, `Scan<Kind>` — never
  through hand-written SQL. Hand-written SQL is allowed only in the bespoke
  comparison arm and in the plain-MergeTree checks, where there is no store.
  Where the store cannot carry the shape, that is a finding, not a licence to
  bypass it.
- **Process measurement.** The generated store is throwaway and is not
  committed: `probe.sh` builds a scratch module beside the tree, copies the
  committed `gen/*.go.tmpl` sources in, generates, compiles and runs. What is
  committed is the input — six templates and a driver, ~700 lines — so its
  size is countable and its shape reviewable.
- **Reporting.** M0 has no domain results to land as facts; the numbers are
  about the substrate, and they live in the logbook and in the ADR's dated
  `## Updates`.

## 5 Running it

Needs a ClickHouse at `$CLICKHOUSE_ENDPOINT` (default `localhost:8123`) and,
for check 11, `rclone` on `PATH`. From the repository root:

```sh
doc/trials/fs-snapshot-store-m0/sql/00-setup.sh                 # scratch db + facts-shaped tables
clickhouse-client --multiquery < doc/trials/fs-snapshot-store-m0/sql/01-block-marks.sql
# … 02 … 07 and extra-purge-projection, each self-contained, in order
doc/trials/fs-snapshot-store-m0/probe.sh                        # checks 5, 8, 9, 10 (generated Go)
doc/trials/fs-snapshot-store-m0/rclone-contracts.sh             # check 11
```

`M0_WORKDIR=<dir> probe.sh` keeps the scratch module so the generated store
can be read. The scratch database is `boxerm0` — not `boxer_m0`, because
`recordstore/gen` refuses a database name that is not `[a-z][a-z0-9]*`.

## 6 Findings ledger

Findings follow the classification scheme in the
[directory convention](../README.md): competence slug × relation
(`missing` / `broken` / `pain`) × ISO 25010 characteristic, severity S1–S4,
evidence in the run directory. Pre-registered candidates, so a later reader
can tell the hypotheses from the surprises: the generator refusing a foreign
table name over the facts schema; `VerifySchema` disagreeing with the
positional decode about what a column is; the `Ingest<Kind>` verb assuming
one row per key; per-block BLAKE3 chaining values not being reachable from
the library's public surface.

## 7 Milestone cut

- **M0 — the eleven checks.** Gate: every check has a pass/fail line with the
  server version and date, and every SD11 item has a decision or an explicit
  "still open" naming the evidence that would settle it. Done 2026-08-19.
- **M0b — re-run on a quiet host.** Only check 8 needs it: the ratio it
  reports is the one number this run does not pin. Gate: three repeats whose
  bespoke arm varies by less than 20%.

## 8 Open questions

1. Whether the emitted `VerifySchema` should learn to ignore `MATERIALIZED`
   columns, or the tree columns should be reached another way. This is a
   change to a shared generator, so it is the user's call, not the trial's.
2. Whether the block ordinal stays a `naturalKey` suffix. The suffix was the
   only encoding measured; the other two were not built, so this run narrows
   the choice by cost but does not close it.
3. Whether a re-run belongs in CI at all. Nothing here is fast, and most of
   it answers a question once.

What M0 decided was built as `public/fs/lading/` (M1) — the throwaway
packages this trial generates are named `fsmeta` / `fsdata` after the tables,
and are not those.
